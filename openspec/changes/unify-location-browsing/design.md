# Design

## Context

See `proposal.md` for the motivation and `specs/trip-attractions/spec.md` plus `specs/location-management/spec.md` for the behavior contract.

当前已保存地点查询分为两条路径：`GET /api/locations/attractions` 要求区域、固定查询景点并支持宠物友好筛选；`GET /api/admin/locations` 可省略区域和类型，按数据库分页查询所有已保存类型。两者分别使用不同的 repository 查询和响应 DTO。类型选项目前由管理服务提供，路由位于 `/api/admin/location-types`。

安全配置要求 `/api/admin/**` 具有 `ADMIN` 角色，其他 `/api/**` 只要求登录。用户地点详情只返回浏览及宠物政策字段；管理员编辑详情还包含原始 POI、商业信息和照片。行程计划只校验地点 `poiId` 已存在于 Pawtrip 数据库，不限制地点类型。

## Goals / Non-Goals

**Goals:**

- 让用户地点页与管理页 Pawtrip 地点表使用同一只读列表 API、分页模型、地点摘要和类型目录。
- 让共享接口仍可区分用户浏览所需的区域和宠物友好过滤，与管理端全量/筛选查询语义。
- 保持 AMap 搜索与地点写入、编辑详情的管理员授权边界。
- 让用户在激活行程城市中按地点类型浏览，并将任意类型地点加入行程。

**Non-Goals:**

- 不开放 AMap 候选搜索、地点创建/更新或原始 POI、商业信息、照片编辑详情。
- 不改变行程计划的数据结构、保存方式或同地点重复加入语义。
- 不新增区域选择器、数据库迁移或第三方依赖。

## Decisions

### D1. 将已保存地点列表与类型目录放在通用登录后读取路径

- 采用共享 `GET /api/locations` 作为已保存地点列表，并以 `GET /api/locations/types` 提供类型选项。用户端与管理端 Pawtrip 地点列表都调用这两个接口。
- 两个接口都位于现有 `/api/**` 登录保护范围内，不属于 `/api/admin/**`。类型目录数据和已保存地点摘要可供所有登录用户读取。
- 管理端的 AMap 搜索、地点创建/更新、管理编辑详情继续留在 `/api/admin/**`。删除或停止使用原用户景点列表与管理员 Pawtrip 列表/类型选项的专用读取路径，避免只统一 service、仍保留两套公开契约。
- 备选方案：仅抽取共享 service/repository、保留两个列表 URL。该方案权限改动更少，但会继续维护两套列表接口契约和客户端查询定义，不符合尽量复用的目标。

### D2. 通过显式查询条件表达两端差异

- 列表接口支持区域、地点类型、宠物友好筛选和分页。用户端始终传入激活行程城市及当前类型；页面默认类型为“景点”，默认开启宠物友好过滤。管理端按现有筛选条件请求，省略区域/类型时仍可查询全部匹配记录。
- 普通用户请求必须带区域条件，管理员可省略区域。服务端不能从当前行程前端状态验证用户所传城市，因此 `/attractions` 页面必须以 `active.cityAdcode` 生成请求，不提供页面内城市选择。
- 使用明确的 `petFriendlyOnly` 语义：用户端默认传 `true`，其筛选条件保持 `maxPetsPerPerson >= 1`；“显示全部地点”传 `false`。管理端不启用该过滤，以保留已保存列表的全量查询行为。分页、区域层级匹配和稳定排序沿用现有数据库列表行为。
- 备选方案：由登录角色隐式决定宠物友好过滤默认值。选择显式参数可避免同一请求因为角色不同而得到不同结果。

### D3. 共享只读地点摘要，不共享管理编辑详情

- 共享列表响应采用一个稳定 DTO，保留用户端的地点类型与完整 `petPolicies`，并包含管理端现有列表需要的基础位置、游玩时间字段和分页元数据。
- 共享列表不包含原始 POI JSON、`business` 或照片详情。用户详情继续使用已有用户端地点详情契约；管理弹窗继续使用管理员详情接口读取编辑所需数据。
- 备选方案：按角色在同一 URL 返回不同 DTO。该做法会令响应契约依赖调用者角色，增加前后端复杂度，故采用所有登录用户一致的列表响应。

### D4. 复用同一地点类型目录

- 将当前管理服务中的类型分组及高德 typecode 映射提取为可被共享只读接口和 AMap 搜索共同使用的目录。用户页和管理员地点筛选页读取同一份 key/label/typecode 数据。
- 目录包含当前已有的景点、住宿、宠物医院、宠物用品店和餐厅；增加类别时只维护一份映射及其测试。
- 备选方案：用户端内置类型选项、管理端继续请求管理接口。该方案导致前后端可能出现不同类别集合，故不采用。

### D5. 将用户卡片行为泛化，不改行程存储

- 地点类型选择和宠物友好筛选变化时重置列表页码；卡片/详情使用共享地点摘要和现有用户详情，沿用逐宠物政策匹配与选择加入天数/暂不排期的交互。
- 后端行程验证已有行为是只确认 `poiId` 存在于 Pawtrip 地点表，不按 `typeGroup` 限制；因此不需要修改行程 API 或 `plan` 结构。

## Risks / Trade-offs

- [共享列表响应新增对所有登录用户可读的管理列表字段] → 仅提供已保存地点摘要、坐标、游玩时间和宠物政策；不返回原始 POI、`business` 或照片详情。
- [共享接口允许管理员省略区域，可能扩大普通用户查询范围] → 服务端要求非管理员请求带区域；用户界面始终从激活行程取城市。服务端当前没有激活行程城市作为可校验的权威状态，因此页面约束与 API 参数验证是不同边界。
- [旧列表路径的内部调用方可能未迁移] → 在同一变更中更新两端 query、API 测试与调用；合并前搜索仓库中旧路径引用。若发现仓库外调用方，再决定是否保留短期兼容别名。
- [类型目录新增类别时 AMap 搜索映射与本地类别可能不一致] → 同一目录同时驱动选项和管理端高德搜索，并为现有类别映射补充测试。

## Migration Plan

1. 先实现通用地点类型目录和共享列表响应/查询，再让用户端及管理端 Pawtrip 列表切换到共享接口。
2. 更新接口权限与测试：普通登录用户可读共享列表和类型目录；管理员专属 AMap 搜索、编辑详情及写入仍要求 `ADMIN`。
3. 更新用户页的类型筛选、地点卡片与详情行为，以及管理页的类型/已保存地点查询；同步 E2E 和知识库架构文档。
4. 在仓库所有调用方迁移并通过测试后，移除旧的专用列表/类型读取路由。若部署环境存在仓库外 API 消费者，则先保留薄兼容别名再单独退役。
5. 无数据库迁移。若发布后需回滚，可恢复旧读取路由和对应前端查询；地点数据与行程计划不需回滚。
