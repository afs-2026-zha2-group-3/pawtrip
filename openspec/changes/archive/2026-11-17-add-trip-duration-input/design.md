# Design

## Context

详见 `proposal.md` 的 Why 与 `specs/trip-duration-input/spec.md` 的行为契约。

当前目的地选择能力在 `/cities` 使用浏览器会话状态保存已选目的地；US-09 行程生成尚未进入当前代码基线。本变更只增加前端会话状态能力，不新增网络请求、服务端接口、数据库字段或行程生成页面。

## Goals / Non-Goals

**Goals**

- 在 `/cities` 候选列表上方提供默认 1 天的可访问 1–7 天步进器，并要求合法天数后才能选定目的地。
- 统一处理步进、手工输入、范围校验和非法值保护。
- 在当前标签页刷新后恢复合法值，并向下游提供经过校验的整数读取结果。
- 在景点页将合法总天数映射为从左到右的天数浏览项。
- 为 US-09 提供“缺少合法天数时阻止生成并回到输入处”的接入契约。

**Non-Goals**

- 不实现 US-09 的页面、生成算法、日程内容或导航路由。
- 不实现景点加入某一天的持久化分配；天数栏仅作为按天浏览容器。
- 不引入服务端持久化、账号维度存储、`localStorage` 或跨标签页同步。
- 不修改目的地候选查询、目的地选择逻辑、应用导航或登出流程。

## Decisions

### D1：使用独立的浏览器会话状态模块

新增聚焦于旅游总天数的前端模块，例如 `apps/web/src/lib/trip-duration.ts`，负责读取、解析、校验、保存和清除总天数。存储使用独立键 `pawtrip.tripDuration`，不复用或修改 `pawtrip.selectedDestination`。

**理由**：总天数和目的地是两个不同的规划输入；独立模块可以让 `/cities` 负责展示，让未来 US-09 直接读取同一契约，并避免修改已归档目的地行为。

**备选方案**：把天数直接写在目的地 store 中会耦合两个生命周期；仅使用组件 `useState` 则无法在当前标签页刷新后恢复；均不采用。

### D2：统一边界校验，读写两端都不信任原始字符串

合法值定义为 `Number.isInteger(value) && value >= 1 && value <= 7`。步进器和输入事件在写入前调用同一校验规则；从 `sessionStorage` 读取时再次解析和校验，非法存储值按“未填写”处理，不能直接交给 US-09。

**理由**：用户可以手工编辑浏览器存储，且 `<input type="number">` 仍可能收到空值、小数或文本；只在 UI 层校验会让下游产生不一致。

**备选方案**：只依赖输入控件的 `min`/`max`/`step` 属性。该方案不能覆盖手工输入和被篡改的存储值，因此不采用。

### D3：前置步进器采用默认值、受控值和显式错误状态

步进器在候选列表加载时默认显示 1，使用受控的输入值，以便在边界操作时保持 1 或 7，并在同一位置展示可访问的错误提示。合法值变化时保存；非法值变化时只更新输入错误状态，保留存储中的最后一个合法值。目的地卡片的「选定」按钮在输入不是合法整数时禁用。

**理由**：AC 要求非法值不覆盖已有合法值，同时需要即时提示；受控输入能明确区分“正在编辑的非法文本”和“已保存的合法总天数”。

**备选方案**：只在表单提交时校验。当前页面没有独立提交步骤，且无法及时反馈边界操作，不采用。

### D4：SSR 不读取浏览器 API，下游通过可验证读取契约接入

浏览器存储只在客户端挂载后读取；服务端渲染/首帧使用空值，避免 SSR 访问 `window`。US-09 通过共享读取函数获得 `number | null`：得到 `null` 时显示必填提示并导航到 `/cities` 的天数输入区域；得到合法整数时继续生成。

**理由**：既有应用使用 TanStack Start/SSR，浏览器 API 不能在模块初始化或服务端渲染阶段直接读取。将“空值判断”放在共享读取契约中，可避免 US-09 重复解析。

**备选方案**：让 US-09 自行读取 `sessionStorage`。会复制校验逻辑并增加漂移风险，不采用。

### D5：不新增依赖，复用现有 Base UI 组件

步进器由现有 `Button`、`Input`、`Label` 等组件组合；布局使用既有 Tailwind 工具类。不会引入新的 UI 库或自定义全局 CSS。

### D6：景点页使用横向天数 Tabs

景点页读取 `useTripDuration()`，以当前合法总天数生成 1 到 N 的横向 Tabs，默认激活第 1 天。切换只改变当前查看的天数标识，不修改景点查询参数或伪造景点分配数据；未来 US-09 可在同一容器中接入按天选择与保存。

## Risks / Trade-offs

- [浏览器禁止 `sessionStorage`] → 读写可能失败；状态模块捕获存储异常，页面不因存储异常崩溃，并将持久化失败作为实现期需要验证的风险。
- [SSR 默认值与会话值不同] → 服务端首帧显示默认 1，客户端挂载后恢复会话中的合法值；受控输入在挂载后同步，不改变服务端数据。
- [用户手工改写存储] → 统一读取校验将非法值视为未填写，US-09 不会拿到越界值。
- [US-09 尚无路由] → 本变更只能验证读取契约，生成入口的回跳 E2E 由 US-09 接入时补齐。
- [目的地重选后天数保留] → 当前设计不隐式清空；用户可以显式重填。若未来按目的地隔离天数，应另行修改数据契约和规格。

## Migration Plan

1. 发布前端状态模块与 `/cities` 步进器；旧用户没有该存储值时按未填写处理。
2. US-09 接入共享读取与必填守卫后，生成流程开始消费合法 `totalDays`。
3. 回滚时移除页面入口即可；遗留的 `sessionStorage` 键不影响既有目的地或认证逻辑。
4. 不涉及数据库迁移、服务端发布或数据回填。

## Open Questions

无会改变本次规格、方案或任务拆分的未决问题。US-09 的具体路由和入口文案属于下游接入细节，由 US-09 变更确定。
