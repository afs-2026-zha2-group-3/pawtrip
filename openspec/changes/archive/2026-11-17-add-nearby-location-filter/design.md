# Design

## Context

见 `proposal.md` 与 `specs/trip-attractions/spec.md`。当前地点浏览页以激活行程城市为唯一范围，支持类型、宠物友好和分页；行程计划只保存 `poiId`，行程面板已按 `poiId` 拉取地点详情并缓存名称与 `typeGroup`；后端 `GET /api/locations` 已返回经纬度，但分页查询不计算距离。`unify-location-browsing` 已完成共享列表接口与类型目录，并已于 2026-11-17 随 origin/main 归档，本设计以其为前置基线。

## Goals / Non-Goals

**Goals:**

- 用页面内状态实现“已排期景点锚点”，不引入新的持久化或地图能力。
- 在共享地点列表接口上以最小增量支持服务端距离过滤、排序与分页，未带参数时保持旧行为。
- 让酒店默认展示列表并在“离景点最近”下拉中选择锚点；餐厅沿用门禁；两类共享同一锚点。
- 让距离结果可验证：固定 5km、Haversine、含边界、无坐标排除、两位端到端夹具可控。

**Non-Goals:**

- 不实现自动推荐、评分、多景点距离聚合或食宿排序策略。
- 不引入地图 SDK、用户定位、驾车距离、路径规划或高德周边搜索。
- 不新增数据库列/迁移，不改变行程 `TripPlan` 结构。
- 不改变管理端地点管理、AMap 搜索、认证授权与共享列表的既有权限边界。
- 不把锚点写入 `sessionStorage`/`localStorage`/服务端。

## Decisions

### D1. 锚点候选由行程计划与既有地点详情缓存派生

- 从 `active.plan.days[].stops` 收集 `poiId`，按 `poiId` 去重；只保留详情缓存中 `typeGroup=attraction` 的地点；`unscheduled` 不参与。
- 复用行程面板已有的地点详情查询（同一 `locationBrowseDetailQueryOptions` 与 TanStack Query 缓存）；缺失详情时按 `poiId` 拉取，加载完成前选择器显示加载态，加载失败的地点不进入候选。
- 备选方案：新增批量地点摘要接口。当前行程 stop 数量有限且详情查询已有缓存机制，新增接口收益不足；若后续候选规模显著增长再单独引入。

### D2. 距离筛选放在服务端，固定 5km，Haversine 在 Java 中计算

- `GET /api/locations` 增加可选 `nearPoiId`；提供时先按现有区域、类型、`petFriendlyOnly` 条件读取候选集合，再在服务端排除无坐标地点、计算 Haversine、过滤 `≤5000m`、按距离升序与 `id` 升序排序，最后在过滤后的集合上分页。
- 未提供 `nearPoiId` 时继续使用现有数据库分页查询与 `ORDER BY id ASC`，避免改变管理端和既有用户行为。
- 备选方案 A：前端拉取全部页并本地过滤。会破坏服务端分页、总数与性能边界，不采用。
- 备选方案 B：SQL 中直接计算 Haversine。SQLite 数学函数可用性依赖编译选项，且当前每城每类型数据量为数百条；Java 计算更可控。若未来单城数据量显著增长，再考虑经纬度包围盒预过滤或空间索引。

### D3. `nearPoiId` 接口保持通用，页面负责“仅餐厅/酒店”策略

- 服务端只校验锚点存在、`typeGroup=attraction`、经纬度非空；不限制候选 `typeGroup`。餐厅/酒店限制是页面行为：只有这两类在已选锚点时传入 `nearPoiId`。
- 这样后端不与页面类型策略耦合，未来其他类型需要距离筛选时无需改接口；规格中的“仅餐厅和酒店”由页面需求保证。
- 服务端不校验锚点是否属于用户激活行程：接口没有行程上下文，页面只提供已排期景点作为候选。

### D4. 酒店默认列表 + “离景点最近”下拉；餐厅保留门禁

- 酒店类型下默认请求并展示该城市已保存酒店；筛选栏提供“离景点最近”下拉，候选为已按天排期的景点，选择后传入 `nearPoiId`、按 5km 过滤、距离升序并重置页码；清除后恢复全量列表。
- 景点类型下保留“行程景点锚点”选择器，供餐厅筛选使用；餐厅未选锚点时仍显示门禁空态且不发起餐厅列表请求。
- 备选方案：酒店也强制先选锚点（上一版）。用户反馈“已把景点加入行程却仍提示选择景点”，且最终酒店页把锚点放在“离景点最近”筛选位，故改为默认列表 + 下拉。
- 宠物医院、宠物用品店不受门禁，保持既有列表行为。

### D5. 锚点状态放在地点浏览页组件内

- `anchorPoiId` 为页面内 `useState`；酒店下拉和景点页选择器共用；切换类型保留；刷新或重新进入页面不保留。
- 当锚点不再出现在候选集合（景点被移出行程）或激活行程 ID 变化时，清除锚点；若当前为酒店，页面恢复默认全量列表；若当前为餐厅，恢复门禁空态。
- 备选方案：写入 `tripStore` 或浏览器存储。锚点是临时浏览条件，不是行程数据；放入 store 会增加持久化与清理负担，且需求已确认不持久化。

### D6. 距离以米返回、以公里展示

- API 返回 `distanceMeters`（整数米）；前端统一格式化为“距{锚点名}约 X.Xkm”，保留一位小数。
- 排序使用服务端未舍入的距离值，距离相同按 `id` 升序；展示舍入不影响排序稳定性。
- `distanceMeters` 仅在带 `nearPoiId` 的请求中返回；未带参数时为 `null` 或省略，现有客户端不受影响。

### D7. 不新增数据库迁移

- `pawtrip_location.longitude/latitude` 已存在且可空；距离实时计算，不落库。
- E2E 夹具需要补充坐标和餐厅/酒店样本，但这是测试数据调整，不是 schema 变更。

## Risks / Trade-offs

- [锚点与候选坐标系不一致] → 只使用高德 POI 的 GCJ-02 坐标，不混入 WGS84 或用户定位；不引入第三方地理编码。
- [坐标为 `NULL`] → 候选排除；锚点返回 `400 VALIDATION_ERROR` 并提示；E2E 夹具当前全部为 `NULL`，任务中必须补齐。
- [距离过滤改变分页语义] → 带 `nearPoiId` 时在过滤后集合上计算总数与分页；用测试覆盖边界、排序和 `hasNext`。
- [锚点名称加载失败或较慢] → 选择器显示加载态；失败候选不出现；不阻塞景点列表本身。
- [跨城锚点导致空结果] → 允许选择，但空态说明“该锚点 5km 内暂无匹配地点”，并保留筛选条件。
- [与 `unify-location-browsing` 叠加] → 该前置 change 已于 2026-11-17 归档；本 change 的 delta 基于统一后的共享列表接口，归档时按现有 Living Spec 合并。
- [单城数据量增长] → 当前在区域/类型/宠物友好集合上做内存距离过滤；任务中保留性能边界说明，数据量显著增长时再下推。

## Migration Plan

1. 先实现后端可选 `nearPoiId` 与 `distanceMeters`，未带参数时保持旧行为；补充 API 测试。
2. 再接入前端酒店默认列表与“离景点最近”下拉、餐厅门禁、距离筛选与展示；补充查询/组件单测与 E2E 夹具。
3. 更新地点 API/浏览页的架构说明。
4. 无 schema 迁移；V23 仅追加珠海测试酒店/餐厅数据，回滚时可单独删除 `test-zhu-%` 记录，不影响既有地点。
5. 按仓库流程完成 P3 验证、P4 实现与 G2/G3；本设计不代签任何人工 Gate。

## Open Questions

无阻塞问题。5km 半径是否可配置、一天多景点的距离聚合口径分别留待后续需求与上游 US-12，不改变本设计的查询契约与任务拆分。
