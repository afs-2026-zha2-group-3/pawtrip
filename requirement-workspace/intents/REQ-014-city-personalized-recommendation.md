# REQ-014 原始意图：城市个性化推荐（按宠物喜好与性格）

> 来源：用户对话诉求（2026-11-17）。编号 REQ-014 经用户确认（顺延登记）。分支 `feat/city-personalized-recommendation`（自 main `c6d1905` 拉取）。

## 用户原话

1. 「拉一个新的分支 实现城市个性化推荐功能」
2. 「需在宠物档案新增宠物喜好 宠物性格 城市个性化推荐按宠物喜好与性格推荐 比如说宠物喜欢游泳 那就城市个性化推荐将海滨城市排在前面」
3. 「用户一进入城市浏览就是个性化推荐的结果 进行了个性化推荐的城市排在前面并在城市卡片的右上角标上系统推荐」（2026-11-17 追加）

## 现状（代码证据，2026-11-17 调查）

- 宠物档案：`pet` 表（V8 建表，V10 名字/肩高，V12 照片，V14 犬种）现有字段为名字、类型（CAT/DOG）、体重、肩高、牵引绳、免疫证明、照片、犬种；**无喜好/性格字段**。
- 档案表单：`apps/web/src/routes/_authenticated/paws.tsx` + `-pet-dialogs.tsx`（创建/编辑/详情弹窗）；API `PetController`（`GET/POST/PUT/DELETE /api/pets`），`PetService.validate` 做服务端校验（非法输入 400 VALIDATION_ERROR）。
- 城市候选：`GET /api/destinations`（`DestinationController`）返回全部城市级行政区（约 369 城，`findByLevelOrderByNameAsc` 名称升序），支持 keyword/petFriendly/petType/breedId/shoulderHeightCm 参数；**城市无海滨/山地/湖泊等特征数据**。
- 前端 `/cities`（`cities.tsx`）：搜索、宠物友好筛选、逐宠物政策匹配标签（`lib/trip/policy-match.ts` 纯函数）、选定行程弹窗。
- 单宠口径先例：`queries/pet-profile.ts` 取第一只宠物，失败/无档案退化 null（REQ-006 design D6）。
- 多值存储先例：`administrative_region.allowed_pet_types` 逗号分隔 TEXT（'CAT,DOG'）。
- 迁移现状：最新 V25（V21/V22 不存在），新迁移自 V26 起。

## 用户已决口径（2026-11-17，全部采纳推荐）

1. **标签词表**：固定标签。喜好（多选）＝游泳、爬山、草地奔跑、城市漫步、玩雪；性格（单选）＝活泼好动、温和平静、胆小敏感。
2. **城市特征覆盖**：种子维护知名旅游城市子集（含珠海/杭州）；未标注城市得分 0 排在后面；不做全部 369 城、不引入外部数据源。
3. **多宠物口径**：取第一只宠物（与现有宠物友好筛选一致）。
4. **排序生效**：默认开启——第一只宠物填了喜好或性格即自动按推荐分排序并显示推荐理由；未填则维持原名称排序；不加开关。
5. **排序架构**：方案 A 前端打分——城市特征标签随候选接口下发，前端纯函数打分排序（与 policy-match 先例一致）；不做后端排序参数。
6. **性格映射**：喜好命中城市特征每项 +2 分；性格加成 +1 分——活泼好动命中户外型城市（海滨/山地/草原/雪景）、温和平静命中湖泊/城市公园、胆小敏感命中城市公园（环境可控）。
7. **编号**：REQ-014。
8. **展示契约（2026-11-17 追加）**：进入 `/cities` 即呈现个性化推荐结果（无需任何操作）；被推荐（得分 >0）的城市排在前面，卡片**右上角标「系统推荐」徽标**；得分 0 无徽标。
9. **NB-1 种子城市清单（2026-11-17 采纳）**：48 城清单全部采纳（已逐一核对 V5 city 级 adcode；直辖市在 V5 为 province 级、本就不在候选内，不含）；完整清单见 requirements/REQ-014 附录。
10. **NB-2 理由文案（2026-11-17 已决）**：仅右上角「系统推荐」徽标，不加推荐理由文字。
11. **NB-3 表单交互（2026-11-17 采纳建议）**：喜好 Checkbox 组多选；性格 Select 单选含「未设置」；详情未填显示「未设置」；沿用 shadcn 组件。
12. **NB-4 同分/0 分（2026-11-17 已决）**：同分维持服务端名称序（稳定排序）；0 分无徽标。

## 方案取舍记录

- A（选定）固定标签 + 前端打分排序：确定性强、可单测、切换宠物无需重新请求。
- B 后端排序：接口契约与前端都要改、切换宠物需重发请求，工作量更大，放弃。
- C 自由文本喜好 + 语义匹配：匹配不确定、无法确定性验收，放弃。
